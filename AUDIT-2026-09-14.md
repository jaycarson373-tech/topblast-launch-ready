# TopBlast launchpad review — September 14, 2026

**Verdict: strong visual direction and a clear product idea; a preview, not an operational launch-and-reward system.**

Site: https://topblast-stonkfun-launchpad.vercel.app

## What changed

- Replaced the generic process card with an interactive, explicitly illustrative Blast Zone example. Visitors can move the price and toggle holding eligibility. The cream/orange/black identity is preserved.
- Explained the holder benefit and the source of rewards. Added a live availability banner; removed unsupported live-reward and next-epoch claims. Exposed Explore and Creator navigation on mobile.
- Fixed token form fields being reset after wallet connection by React's successful form-action reset behavior. Frozen quote details cannot be edited before signing; submission uses the exact prepared logo.
- Stored the payment signature before the venue submission, persisted a public recovery receipt in the browser, and added status recovery after refresh. Unknown submission results do not offer another payment. This is recovery protection, not a claim that all distributed-transaction failure cases are solved.
- Rejected unknown/incomplete venue success responses and preserved failed status. Checked returned payment IDs against the signed transaction ID.
- Acknowledged Helius webhooks only after persistence. A failed write returns 503 so delivery can retry; activity inserts have deduplication keys.
- Fixed UI token amounts being interpreted with zero decimals; used tracked mint decimals, rejected unsafe numeric conversions, and ignored failed transactions.
- Added an unapplied database migration enabling RLS on operational tables and fixing reward totals multiplied by snapshot joins. Eligibility counts now refer to the latest completed epoch.
- Made production verification fail when launches or rewards are unready. The separate `--smoke` option tests availability only.

## Verified

- 34 unit/regression tests pass; lint, TypeScript, and the production build pass.
- Headless Chrome tested the actual rendered site at 320, 390, 768, and 1440 px: navigation, example slider, holding toggle, page routes, horizontal overflow, unavailable launch controls, and an injected API failure. No uncaught page errors in those checks.
- A simulated Wallet Standard wallet and intercepted venue responses exercised prepare, frozen review, sign/submit, processing, reload, and status recovery. Exactly one submission occurred. This test did not connect a real wallet, spend funds, or contact the venue submission endpoint.
- Both migrations ran against local PGlite PostgreSQL. Tests verified independent reward totals, latest-epoch eligibility, RLS on all public tables, and blocked anonymous control-plane access. PGlite used built-in UUID generation; installing the production pgcrypto extension was not tested.
- Vercel deployment was tested separately from source compilation. Public health reports the infrastructure gaps listed below. Strict production verification correctly fails; page availability checks pass.

## Release blockers

1. Production has no configured Supabase database, Helius webhook credentials, or reward/protocol treasury addresses. Launches are disabled and dry-run mode is enabled. The second SQL migration has therefore NOT been applied to a production database.
2. The current `scripts/reward-worker.ts` is a monitor/dry-run allocation logger. It does not connect `buildEpochPlan` or `runEpochJob` to persistent jobs, finalized snapshots, budget reservation, signing, payout confirmation, or balance reconciliation. Setting environment variables will not implement those missing steps.
3. Creator-fee deposits are not wired into verified funding events. StonkFun's documented standard launch API sends fees to the creator; it does not expose the arbitrary fee-recipient split promised by a simple allocation slider. A real funding design and per-launch attribution are required before the reward loop can operate.
4. The indexer still needs venue-specific transaction verification, actual mint-decimal discovery, finalized/history reconciliation, out-of-order delivery handling, and restart/backfill acceptance tests. Its current transfer heuristics alone are not sufficient evidence for production payouts.
5. Market metrics have database fields but no verified continuous pricing ingestion. Token/holder pages and proof histories have no real production launch data to validate.
6. Payout execution is absent. Exporting an allocation manifest does not execute a payout or prove confirmation. Real-money acceptance must verify the treasury, asset, recipients, funded cap, and retry/reconciliation behavior.

## Required end-to-end acceptance

Connect the dedicated database and indexer; apply both migrations; implement the funding and persistent reward pipeline; then conduct one controlled launch. Verify an actual buyer, transfer/sell exclusions, finalized entry basis, attributable funding, one funded epoch, payout confirmations, public proof, and restart without duplicate allocation or payment. Demonstrate isolation with a second launch before opening permissionless creation.

No real launch, wallet signature, fee transfer, or payout was performed during this review. The launch and payout locks remain in place.
